## 0. 项目一句话定位

Omni 是一个类大麦网票务平台，采用 **B 端主导、C 端参与** 的业务模式：

- C 端：活动/巡演浏览、搜索、详情、选座、抢票、候补、小队抢票、订单、支付、退款、电子票、订阅提醒、客服。
- B 端：平台后台、主办方后台、客服后台、运营后台，统一挂在前端 `/console/*` 路由下。
- 后端：Java Spring Cloud 微服务 + NestJS 抢票/候补服务 + PostgreSQL 生产物理拆库。
- 当前运行口径：`prod-split`，票务运行库必须是 `omni_ticket_split`，不要把历史共享库 `omni_ticket` 恢复为当前业务运行库。

### 1.2 前端状态管理与请求封装

当前项目 **没有** 使用 Redux、Pinia、Vuex、Zustand。主要状态分散在 React `useState/useMemo/useEffect` 和浏览器 `localStorage`。

认证状态来源：`frontend/src/lib/auth.ts`

注意：

- 代码当前使用 `omni_token` / `omni_user`。
- 兼容迁移旧 key：`damai_token` / `damai_user`。
- 若后续修改登录态，应以 `frontend/src/lib/auth.ts` 的当前实现为准。

网络请求来源：`frontend/src/lib/api.ts`

- 没有 Axios。
- 统一使用 `request<T>()` 基于 `fetch` 封装。
- 自动注入 `Authorization: Bearer <token>`。
- 后端返回格式为 `ApiResult<T>`，只有 `code === 200` 才返回 `data`。
- 英文错误会被映射为中文用户可见文案。

关键片段：

```ts
async function request<T>(url: string, options?: RequestInit, config?: { timeoutMs?: number }): Promise<T> {
  const token = getToken()
  const headers: HeadersInit = {
    'Content-Type': 'application/json',
    ...(token ? { Authorization: `Bearer ${token}` } : {}),
    ...options?.headers,
  }

  const response = await fetch(`${BASE_URL}${url}`, {
    ...options,
    headers,
    signal: controller.signal
  })

  const result: ApiResult<T> = await response.json()
  if (result.code !== 200) {
    throw new ApiError(result.code, toUserVisibleMessage(result.message))
  }

  return result.data
}
```

### 1.5 数据库拓扑

当前推荐运行模式为 `prod-split`：

| 服务 | 数据库 |
| --- | --- |
| `java-user` | `omni_user` |
| `java-ticket` | `omni_ticket_split` |
| `java-order` | `omni_order` |
| `java-payment` | `omni_payment` |
| `java-notification` | `omni_notification` |
| `grab-service` | `omni_grab` |
| `java-gateway` | 不连接业务数据库 |

重要边界：

- `java-order` 不直接访问 user/ticket 表；通过 `java-user` 和 `java-ticket` internal API 完成用户校验、报价、库存锁定、座位锁定、确认售出和释放。
- `java-payment` 不直接访问 order/user/ticket 表；通过 `java-order`、`java-user`、`java-ticket` 的 internal API 协作。
- 禁止新增跨服务 Mapper、Entity、XML mapper 或 SQL join。
- 所有新增 internal API 必须校验 `X-Internal-Token`。

### 3.3 菜单渲染方式

当前菜单是 **前端静态配置 + 前端权限过滤**，不是后端动态获取菜单。

核心逻辑位于 `frontend/src/app/console/layout.tsx`：

```ts
const visibleMenuItems = useMemo(() => {
  if (checking || !role) return []
  if (isPlatformAdminRole(role)) {
    return menuItems.filter((item) => canAccessConsolePath(item.href, permissionCodes))
  }
  if (role === 'organizer') return organizerMenuItems
  if (permissionCodes.length > 0 || role === 'organizer_admin') {
    return menuItems.filter((item) => {
      return canAccessConsolePath(item.href, permissionCodes)
    })
  }
  return menuItems.filter((item) => {
    if (!('roles' in item) || !item.roles) return true
    return item.roles.includes(role as 'admin' | 'organizer')
  })
}, [checking, role, permissionCodes])
```

渲染流程：

1. `ConsoleLayout` 进入后调用 `getUserInfo()`。
2. 从后端拿到 `role` 和 `permissionCodes`。
3. 用 `canEnterConsole()` 判断是否能进后台。
4. 用 `canAccessConsolePath()` 或 `isConsolePathAllowedForRole()` 判断当前路径。
5. 过滤 `menuItems` 或直接使用 `organizerMenuItems`。
6. 侧边栏通过 `visibleMenuItems.map(...)` 渲染。

路径权限判断：

```ts
function getPathPermission(pathname: string): string[] {
  if (pathname === '/console' || pathname === '/console/profile') return ['*']
  if (pathname.startsWith('/console/tours/')) return ['tour.manage']
  const exact = PATH_PERMISSION_MAP[pathname]
  if (exact) return exact
  for (const [prefix, perms] of Object.entries(PATH_PERMISSION_MAP)) {
    if (pathname.startsWith(`${prefix}/`)) return perms
  }
  return []
}

export function canAccessConsolePath(pathname: string, permissionCodes: string[]): boolean {
  const required = getPathPermission(pathname)
  if (required.length === 0) return false
  if (required[0] === '*') return true
  return required.some(p => permissionCodes.includes(p))
}
```

- `organizer_admin`：平台主办方运营员，面向平台招商、主办方管理、账号、场馆审核、运营跟进等。

```java
    User user = userMapper.selectById(userId);
    String effectiveRole = resolveRole(user, resolveSupportAccount(user));
    List<String> permissions = ROLE_PLATFORM_SUPER_ADMIN.equals(effectiveRole)
            ? listAllPermissionCodes()

    response.setEffectiveRole(effectiveRole);
    response.setSupportRole(resolveSupportRole(effectiveRole));
```

角色解析规则：

```java
private static String resolveRole(User user, SupportAccount supportAccount) {
    String role = user.getRole();
    if (role == null) return "user";
    switch (role) {
        case "admin": return ROLE_PLATFORM_SUPER_ADMIN;
        case "support": return resolveSupportAccountRole(supportAccount);
        case "organizer": return "organizer";
        default: return role;
    }
}
```

## 7. 关键业务数据流

### 7.1 C 端购票主链路

```text
用户登录
  -> frontend/src/lib/api.ts login()
  -> Gateway /api/user/login
  -> java-user 生成 token + role + permissionCodes

浏览/搜索活动
  -> listActivities()
  -> Gateway /api/ticket/activities
  -> java-ticket ActivityController
  -> Elasticsearch ActivitySearchProvider

进入活动详情
  -> getActivityDetail()
  -> java-ticket ActivityService
  -> 返回 ActivityDetailVO = activity + category + artist(s) + sessions + ticketTypes

下单
  -> createOrder() 或 createOrderWithSeats()
  -> java-order OrderController
  -> java-user internal 校验用户/实名观演人
  -> java-ticket internal sales quote/lock-stock/lock-seats
  -> java-order 写 order-owned order_snapshot / order_seat / order_attendee
  -> java-ticket confirm-sold

支付
  -> createAlipayPagePay() / createAlipayQrPay()
  -> java-payment AlipayController
  -> 回调或 sync 后通知 java-order 标记 paid
  -> java-order 生成 electronic_ticket / 票夹
```

### 7.2 抢票链路

```text
用户提交抢票
  -> frontend submitGrabRequest()
  -> Gateway /api/grab/requests
  -> NestJS grab-service
  -> Redis 排队/幂等/进度
  -> java-ticket internal 锁库存/锁座
  -> java-order internal 创建订单
  -> 进度轮询 getGrabProgress()
  -> 成功后用户支付订单
```

### 7.3 候补链路

```text
用户登记候补
  -> createWaitlistEntry()
  -> /api/waitlist/entries
  -> grab-service waitlist module 写 omni_grab

票释放或补偿触发
  -> RabbitMQ / waitlist allocator
  -> 锁库存并生成 offer/order
  -> 通知用户支付
```

### 7.4 B 端后台链路

```text
进入 /console/*
  -> ConsoleLayout 调 getUserInfo()
  -> java-user 返回 role + permissionCodes
  -> canEnterConsole / canAccessConsolePath
  -> 渲染静态菜单或跳转默认后台路径

后台活动/巡演/场次/票档
  -> frontend console pages
  -> /api/ticket/admin/**
  -> java-ticket UserAccessService 调 java-user internal auth context
  -> 校验 permissionCodes / scopeType / scopeId

后台 RBAC/账号/审计/对账/异常任务
  -> /api/user/console/**
  -> java-user InternalWorkbenchController
  -> requirePermission / requireAnyPermission
  -> 写 operation_audit_log
```

## 8. 后续开发必须遵守的项目边界

1. 前端请求必须优先走 `frontend/src/lib/api.ts` 的 `request<T>()`，不要引入 Axios。
2. 前端新增能力必须有真实后端接口支撑；不要只做 mock/offline 降级。
3. B 端页面必须挂在 `/console/*` 并通过 `ConsoleLayout` 权限体系。
4. 后台菜单当前是静态配置；新增 B 端入口时通常要同步：
   - `frontend/src/app/console/layout.tsx`
   - `frontend/src/lib/console-auth.ts`
   - `frontend/src/lib/console-paths.ts`（如果是 organizer 白名单/辅助路径）
   - 后端 RBAC SQL 或权限服务
5. 新增权限码必须进入 `rbac_permission`，并按角色进入 `rbac_role_permission`。
6. Java 服务之间禁止新增跨服务 Mapper/Entity/XML mapper/SQL join。
7. `java-order` 不直接查 ticket/user 表；通过 internal API。
8. `java-payment` 不直接查 order/user/ticket 表；通过 internal API。
9. 新增 internal API 必须校验 `X-Internal-Token`。
10. 票务运行库是 `omni_ticket_split`，不要恢复 `omni_ticket` 为运行库。
11. 搜索强依赖 Elasticsearch；不要恢复 PostgreSQL 搜索 fallback。
12. 动态系统禁止恢复：不要恢复 `MomentSection`、`SocialController`、moment API 或旧 social/moment 持久化代码。
13. 用户可见文案必须中文。
