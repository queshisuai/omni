## 需要调整或补齐

| 问题 | 证据 | 建议 |
|:---|:---|:---|
| 历史 `sql/seed.sql` 容易被误用 | 仍包含共享库式初始化、模拟活动、`review` 清理等历史内容 | 在文档中标明“历史共享库 seed”，后续演示只使用 real-demo seed。 |
| 评价/问答数据不足 | 评价系统重新纳入，但 real-demo seed 当前重点在票务、订单、通知、抢票 | 增加活动评价、购前问答、待审核/已隐藏/举报状态数据。 |
| 入场核验演示不足 | 电子票 seed 存在，但缺核验记录、线下设备同步、重复扫码、异常补录等场景数据 | 增加未入场、已验票、无效、转赠后票据、成功核验、重复扫码、退款后拒绝、设备停用等组合。 |
| 候补/小队页面展示 ID | waitlist/team 前端仍有活动、场次、票档 ID 展示 | seed 可保留 ID，但接口或前端需要补充名称字段。 |
| 平台主办方运营员角色命名不一致 | SQL 和前端仍使用 `organizer_admin` / 主办方管理员 | 如果改名，需要新增迁移和 seed 同步调整。 |
| 通知场景不够统一 | 目前通知 seed 已有站内通知，但通知事件中台还未统一 | 后续按通知事件模型补 `aggregateKey`、模板、渠道状态等数据。 |

## 数据库变更纪律

- 只改种子数据，不等于完成结构变更。
- 新增表、字段、索引、约束必须写到对应 `sql/production-split/{service}` 目录。
- 结构迁移写完后，需要执行本地数据库迁移，再验证代码。
- 种子数据必须和当前五库拓扑一致，不写入旧 `omni_ticket` 作为默认业务库。
- 涉及用户、订单、票务跨服务数据时，只保存 copied id 或快照，不新增跨库外键。
