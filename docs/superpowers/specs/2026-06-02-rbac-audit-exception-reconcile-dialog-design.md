# RBAC、审计、异常补偿、对账与后台弹窗一期设计

> 目标：先打稳后台权限底座，再把关键人工操作和高风险链路串进审计、异常补偿与日结对账，最后清掉后台原生弹窗。

## 1. 背景

当前后台仍以 `admin / organizer` 两个大角色做页面级判断，`support_account` 也已存在，但客服主管、普通客服、平台超管等后台身份还没有独立落点。与此同时，客服账号管理、退款审核、风控处理、站点变更审核、场馆审核等高风险后台操作，缺少统一的权限控制和可追溯审计。

前端后台还残留 `window.prompt / window.confirm / alert`，这会让确认、危险确认、原因输入等交互分散在各页面，后续也不利于统一治理。

## 2. 目标与分期

### P0

- 建立后台单主角色 + 权限点模型
- `java-user` 成为权限归属服务
- 改造高风险后台接口的鉴权入口
- 替换后台原生弹窗

### P1

- 建立全链路人工操作审计
- 先接入后台写操作审计
- 再补支付、退款、出票、入场核验的业务链路事件

### P2

- 建立异常任务与补偿后台
- 建立日结对账与差异记录
- 后续再扩展外部账单导入比对

## 3. 角色与权限模型

### 3.1 角色定义

后台只保留一个主角色字段，不做多角色叠加：

- `platform_super_admin`：平台超管
- `support_manager`：客服主管
- `support_agent`：普通客服
- `organizer_admin`：主办方管理员

现有登录态里的 `role` 字段将作为后台主角色继续沿用，只是枚举值从旧的 `admin / organizer / support` 逐步迁移到新的后台主角色集合；前端和后端都需要保留旧值兼容一段时间。

`support_account` 增加业务角色字段 `support_role`，用于区分客服主管与普通客服。平台超管不归入 `support_account`，而是直接归入后台用户体系。

### 3.2 权限点

权限点按动作拆分，不按页面粗粒度拆分。首批至少包括：

- 客服会话
- 客服账号
- 活动审核
- 退款审核
- 风控处理
- 审计查看
- 对账查看
- 补偿执行

后续再按具体接口补充更细的子权限。

### 3.3 权限判定规则

- 后台登录态只携带主角色标识
- 具体接口通过权限点判断是否可访问
- 主办方管理员只能访问自己业务范围的数据
- 平台超管拥有全局查看权和高危补偿执行权
- 客服主管可管理客服会话和客服账号
- 普通客服只能处理被分配或允许范围内的客服工作

## 4. `java-user` 权限归属服务

`java-user` 负责维护角色、权限点、`support_role` 以及内部查询接口，作为其他业务服务的权限事实源。

### 4.1 数据职责

- 用户主角色
- 用户权限点集合
- 客服账号的 `support_role`
- 主办方管理员的业务归属范围

### 4.2 内部接口

建议提供内部权限查询接口，供各业务服务在请求进入时查询：

- 当前用户主角色
- 当前用户拥有的权限点
- 当前用户业务归属范围
- 当前用户是否允许执行高危动作

接口形式保持内部服务风格，不对外暴露给前端直接依赖。

### 4.3 迁移原则

- 先保留现有 `admin / organizer` 兼容逻辑
- 新权限接口上线后，高风险后台接口优先接入
- 前端菜单只做展示收敛，不作为唯一安全边界

## 5. 后端改造范围

### 5.1 先改的高风险后台接口

首批优先接入权限控制的接口：

- 客服账号管理
- 退款审核
- 风控审核 / 风险处理
- 站点变更审核
- 场馆审核

这些接口必须做到：

- 先校验主角色和权限点
- 再校验业务归属范围
- 再执行业务动作
- 最后写审计日志

### 5.2 业务服务落地方式

每个业务服务本地加一层轻量鉴权适配器，避免把所有权限判断都塞到网关。

原因：

- 业务归属往往依赖本服务数据
- 审计日志需要拿到动作、目标对象和结果
- 高危动作往往需要事务内补写补偿或失败原因

## 6. 全链路人工操作审计

### 6.1 审计表

新增 `operation_audit_log`，记录人工操作。

核心字段建议：

- `id`
- `operator_id`
- `operator_role`
- `action`
- `target_type`
- `target_id`
- `target_ref`
- `reason`
- `result`
- `success`
- `error_message`
- `trace_id`
- `create_time`

其中：

- `target_ref` 记录人工可读的业务引用号，例如订单号、退款单号、活动 ID、站点 ID、场馆 ID
- `result` 记录一句简短结果说明，必要时再配套结构化结果字段

### 6.2 审计写入时机

先接入后台写操作：

- 客服账号管理
- 站点审核
- 退款审核
- 活动上下架
- 风险处理

写入原则：

- 成功、失败都要记
- 失败要保留业务错误原因
- `traceId` 必须贯穿一次请求
- 审计记录尽量在业务动作结束后落库
- 失败场景也要落审计，便于事后补查

### 6.3 链路事件补充

后续补业务链路事件：

- 支付
- 退款
- 出票
- 入场核验

统一按以下关联键串联：

- 订单号
- 支付单号
- 退款单号
- 票号

## 7. 异常任务与补偿后台

### 7.1 异常模型

新增异常案例 / 补偿任务模型，覆盖：

- 异常退款
- 重复支付
- 库存扣减失败
- 出票失败
- 核验冲突

### 7.2 后台能力

新增“异常任务”列表，支持：

- 筛选
- 查看证据
- 标记处理
- 触发补偿

### 7.3 权限控制

高危补偿动作只允许：

- 平台超管
- 或特定补偿权限用户

普通客服和主办方管理员不得直接执行高危补偿。

## 8. 日结对账

### 8.1 数据模型

新增：

- 对账批次
- 对账明细
- 差异记录

### 8.2 第一阶段算法

先基于现有 `payment / refund_request` 做本地日结汇总，不直接拉外部支付平台账单。

输出内容至少包括：

- 当日支付汇总
- 当日退款汇总
- 成功数 / 失败数
- 账实差异

### 8.3 后续扩展

后续再接入支付宝账单导入和比对，不影响一期本地日结模型。

## 9. 后台弹窗统一

### 9.1 替换范围

替换后台所有 `window.prompt / window.confirm / alert`。

### 9.2 `GlobalDialog` 能力

统一支持：

- 确认
- 危险确认
- 原因输入
- 文本域备注

### 9.3 前端约束

增加前端检查，禁止 `frontend/src/app/console` 再出现原生弹窗调用。

建议把检查做成 lint 或脚本校验，纳入日常验证。

## 10. 前端权限呈现

前端只做展示收敛，不做最终授权。

- 平台超管看到审计、对账、异常任务和补偿入口
- 客服主管看到客服会话和客服账号
- 普通客服只看到可处理范围
- 主办方管理员只能看到自己业务范围

现有 `frontend/src/app/console/layout.tsx` 里基于 `admin / organizer` 的菜单判断，需要逐步迁移到新权限模型。

## 11. 兼容与迁移

### 11.1 兼容策略

- 保留旧角色字段读取
- 新权限接口逐步替换前端和后台判断
- 旧页面先能跑，再逐步收口

### 11.2 迁移顺序

1. `java-user` 角色与权限点底座
2. 高风险后台接口接权限
3. 后台弹窗统一
4. 审计日志
5. 异常任务与补偿
6. 日结对账

## 12. 验收标准

- 普通客服不能管理客服账号
- 客服主管可以管理客服会话和账号
- 主办方管理员只能看 / 处理自己业务范围
- 平台超管可查看审计、对账、异常任务并执行补偿
- 后台不再直接调用 `window.prompt / window.confirm / alert`
- 关键后台写操作都能在审计日志里追到操作人、对象、原因和结果

## 13. 风险与约束

- 现有后台菜单和接口大量依赖旧角色判断，迁移期需要兼容
- 审计必须覆盖失败路径，否则可追溯性不完整
- 高危补偿动作必须走强校验，不能只靠前端按钮隐藏
- 对账一期不接外部账单，避免把范围拉爆
