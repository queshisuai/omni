# 抢票低风险固化与 Sentinel 最小启用设计

## 背景

抢票核心高风险项已经完成一轮加固：grab-service 从登录态获取用户身份，状态机、结果查询、取消接口、补偿任务已有基本实现；订单创建后可进入现有支付与退款链路。当前剩余优化应避免扩大行为变更，先把这些已满足项固化为可回归验证，再小范围启用 Sentinel 限流/熔断能力。

项目已有 `spring-cloud-starter-alibaba-sentinel` 依赖预埋在五个 Java 业务服务中，但当前未发现实际 Sentinel 资源注解、降级处理或规则配置。gateway 暂未作为第一优先级，除非现有依赖和配置已经支持低成本接入。

## 目标

1. 用测试固定 grab-service 的登录态身份、状态查询、取消和补偿行为。
2. 小范围启用 Sentinel，优先保护订单创建或票务库存相关的高流量入口。
3. Sentinel 限流/降级时返回稳定业务响应，不产生 500 或异常堆栈外泄。
4. 保持现有订单、支付、退款主流程不变。

## 非目标

1. 不引入 Sentinel 控制台作为本轮必需运行依赖。
2. 不做全站限流平台化改造。
3. 不改 grab-service 状态枚举和数据库结构。
4. 不把支付、退款或订单超时逻辑迁入 grab-service。

## 方案

### 一、先固化 grab-service 已满足项

在现有 NestJS 测试基础上补齐低风险回归约束：

- 提交抢票请求时，`userId` 只能来自认证后的 request user；即使 body 带 `userId` 也不参与服务调用。
- 结果查询只能查询自己的抢票请求，其他用户请求返回禁止访问。
- 取消接口只能取消未创建订单且仍处于可取消状态的请求；终态或已有订单请求保持原状态。
- 补偿任务只处理超时且未产生订单的请求，并释放 Redis hold；已有订单请求不释放。

这些测试不改变业务行为，只约束当前实现。

### 二、Sentinel 最小启用

优先在已有 Sentinel 依赖的 Java 业务服务中选择单个入口启用资源保护：

- 首选订单服务创建订单入口，因为抢票成功后会集中进入订单创建链路。
- 如果订单服务中创建订单逻辑拆分为普通票与选座票两个入口，应分别使用清晰资源名。
- 资源 block handler 返回 `Result` 业务失败响应，提示“系统繁忙，请稍后重试”。
- 规则使用本地初始化方式，设置保守阈值，确保本地能验证生效；阈值后续可按压测结果调整。

### 三、验收

1. grab-service 单测通过。
2. 相关 Java 服务编译或单测通过。
3. 正常订单创建不受影响。
4. 触发 Sentinel 限流时返回稳定业务失败响应，不返回 500。

## 风险控制

- 先加测试再改 Sentinel 行为，避免已有满足项回退。
- Sentinel 本轮只保护一个链路，降低误伤范围。
- 降级响应只表达系统繁忙，不暴露内部异常。
- 不修改数据库、不调整跨服务边界。
