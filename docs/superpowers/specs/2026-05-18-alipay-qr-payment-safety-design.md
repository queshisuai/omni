# 支付宝二维码支付与取消前查账保护设计

## 背景

当前支付链路使用支付宝网页支付：前端调用 `POST /api/payment/alipay/page-pay` 获取支付宝表单，然后直接提交表单跳转到支付宝页面。支付完成后依赖支付宝回跳到 `/payment/result`，再由前端调用 `GET /api/payment/alipay/sync/{orderId}` 查询支付宝并补偿本地订单状态。

这个链路存在账务风险：用户在支付宝已经付款，但因为回跳失败、网络异常、通知不可达或同步接口失败，网站本地订单仍显示为待支付。此时用户仍可以取消订单，导致本地订单取消、支付宝账单已支付，后续查账和退款都会出现不一致。

用户希望改为站内支付弹窗：显示产品、金额、待支付状态、订单号、支付二维码和刷新状态按钮，不再强依赖跳转支付宝页面。

## 目标

1. 防止“支付宝已付款但本地待支付时仍能取消订单”的坏账风险。
2. 支持站内支付宝二维码支付弹窗，降低对支付宝回跳页面的依赖。
3. 支付状态以支付宝真实查询结果为准，必要时补偿本地订单状态。
4. 支付金额以后端订单金额为准，不信任前端金额。
5. 保留现有异步通知和同步查询能力，形成多层确认机制。

## 非目标

1. 不做真实移动端支付宝 SDK 支付。
2. 不引入复杂支付状态机，只在现有订单状态和支付流水状态上补齐保护。
3. 不处理支付宝配置、证书、公私钥部署之外的新密钥体系。
4. 不提交或输出任何支付宝私钥、公钥敏感内容。

## 核心方案

采用“站内二维码支付 + 前端轮询/手动刷新 + 后端取消前查账保护”。

### 支付创建

新增支付宝扫码支付接口：

`POST /api/payment/alipay/qr-pay`

请求：

```json
{
  "orderId": 123
}
```

响应：

```json
{
  "orderId": 123,
  "orderNo": "DM20260518123456ABCDEF",
  "amount": 560.00,
  "subject": "万象票务订单 DM20260518123456ABCDEF",
  "qrCode": "https://qr.alipay.com/..."
}
```

`java-payment` 调用支付宝预创建扫码支付能力生成 `qrCode`。推荐使用 `alipay.trade.precreate` 对应 SDK 请求。后端只返回二维码内容字符串，前端负责渲染二维码图片。

### 支付弹窗

活动详情页确认订单后，不再提交支付宝表单跳转。流程改为：

1. 创建订单。
2. 调用 `qr-pay` 获取二维码。
3. 打开站内支付弹窗。
4. 弹窗展示活动/票档、金额、订单号、待支付状态、支付宝二维码。
5. 弹窗自动轮询 `GET /api/payment/alipay/sync/{orderId}`。
6. 用户也可以点击“刷新状态”立即同步。
7. 同步到已支付后，弹窗展示支付成功，并提供“查看订单”和“继续浏览”。

订单页的“去支付”也复用同一个二维码弹窗。待支付订单额外提供“刷新状态”按钮，便于用户在关闭弹窗、网络中断或异步通知延迟后手动补偿。

### 支付同步

继续复用现有 `syncByOrderId(orderId)` 作为唯一的主动查账入口：

1. 读取本地订单。
2. 查询支付宝交易状态。
3. 如果支付宝返回 `TRADE_SUCCESS` 或 `TRADE_FINISHED`，校验金额。
4. 金额一致时标记支付流水成功。
5. 通过内部接口调用 `java-order` 标记订单为已支付。
6. 返回订单状态、支付状态、交易号和提示文案。

这个接口要保持幂等：重复调用已支付订单时返回成功，不重复扣减库存或重复售座。

### 取消订单保护

仅靠前端隐藏按钮不安全。取消订单必须在后端阻断坏账。

待支付订单取消前增加查账保护：

1. `java-order` 收到取消订单请求。
2. 如果订单不是待支付，按现有逻辑拒绝。
3. 如果订单是待支付，先调用 `java-payment` 的内部支付同步/确认接口。
4. 如果支付宝确认已支付：
   - `java-payment` 补偿本地支付流水。
   - `java-order` 订单被标记为已支付。
   - 取消接口返回失败，提示“订单已支付，不能取消”。
5. 如果支付宝确认未支付或查无交易：
   - 允许取消。
   - 释放锁座。
6. 如果支付宝查询失败或结果未知：
   - 拒绝取消。
   - 返回“支付状态确认中，请稍后刷新后再操作”。

为避免服务循环依赖过重，可以新增 `java-payment` 内部接口，例如：

`POST /api/payment/internal/alipay/sync-order/{orderId}`

由 `INTERNAL_API_TOKEN` 保护。该接口复用 `syncByOrderId` 的查账逻辑，并返回可供订单服务判断的状态。

## 组件边界

### java-payment

职责：

1. 生成支付宝扫码支付二维码。
2. 管理本地支付流水。
3. 处理支付宝异步通知。
4. 主动查询支付宝交易状态。
5. 支付成功后调用订单服务内部接口标记已支付。

新增/调整：

1. `QrPayResponse` DTO。
2. `AlipayService.createQrPay(orderId)`。
3. `AlipayController.qrPay(...)`。
4. 内部同步接口，供 `java-order` 取消前调用。

### java-order

职责：

1. 创建待支付订单。
2. 维护订单状态。
3. 支付成功时标记订单已支付并售座/扣库存。
4. 取消订单时释放锁座。

新增/调整：

1. 新增 `PaymentInternalClient` 调用支付服务内部同步接口。
2. `cancelOrder(id)` 在待支付订单取消前先确认支付宝状态。
3. 支付状态未知时拒绝取消，避免坏账。

### frontend

职责：

1. 展示站内支付弹窗。
2. 渲染二维码。
3. 自动轮询和手动刷新支付状态。
4. 支付成功后刷新订单列表或跳转订单页。

新增/调整：

1. 新增 `createAlipayQrPay(orderId)` API。
2. 新增可复用 `AlipayQrPayModal` 组件。
3. 活动详情页确认支付改为打开二维码弹窗。
4. 订单页“去支付”改为打开二维码弹窗。
5. 订单页待支付订单增加“刷新状态”。

## 数据流

### 新购票支付

```text
用户确认支付
→ frontend 创建订单
→ java-order 创建待支付订单并锁座
→ frontend 请求 java-payment 生成二维码
→ java-payment 查询订单金额并创建/复用待支付流水
→ 支付宝返回 qrCode
→ frontend 展示二维码弹窗
→ 用户扫码支付
→ 支付宝异步通知或 frontend 轮询 sync
→ java-payment 查支付宝并校验金额
→ java-payment 调 java-order markPaid
→ java-order 标记订单已支付、座位已售、扣库存
→ frontend 展示支付成功
```

### 取消待支付订单

```text
用户点击取消订单
→ frontend 调 java-order DELETE /api/order/{id}
→ java-order 发现订单为待支付
→ java-order 调 java-payment 内部同步接口
→ java-payment 查询支付宝
→ 已支付：补偿订单为已支付，取消失败
→ 未支付：java-order 取消订单并释放锁座
→ 查询失败/未知：取消失败，提示稍后刷新
```

## 错误处理

1. 生成二维码失败：前端弹窗不打开，提示“生成支付二维码失败”。
2. 支付宝查询失败：前端显示“支付结果确认中”，允许继续刷新。
3. 取消前查账失败：后端拒绝取消，避免误取消已付款订单。
4. 支付金额不一致：后端拒绝标记支付成功，并返回错误，保留人工处理空间。
5. 本地订单已支付：二维码接口返回“订单已支付”，前端刷新订单状态。
6. 订单已取消/已退款：二维码接口拒绝重新支付。

## 安全与配置

1. `INTERNAL_API_TOKEN` 必须显式配置，不能使用固定默认值。
2. `java-order` 调用 `java-payment` 内部接口必须带内部令牌。
3. 支付宝私钥、公钥不写入代码、不输出到日志、不提交 Git。
4. 支付金额以后端订单金额为准。
5. 取消订单的最终保护在后端完成，前端只是体验优化。

## 部署注意

1. 需要保证 `java-payment` 可以访问支付宝网关。
2. 本地开发环境即使没有公网异步通知，仍可通过轮询/手动刷新补偿状态。
3. 生产环境仍应配置支付宝 `notify_url`，异步通知作为第一层自动确认。
4. 前端需要引入二维码渲染依赖，或使用轻量二维码生成组件。
