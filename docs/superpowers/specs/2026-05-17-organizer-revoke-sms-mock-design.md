# 主办方取消资格与短信验证码 Mock 设计文档

> **适用于执行的工作流**：先完成设计确认，再进入实施计划。涉及后端与前端联动，且包含退款与权限变更，请按任务逐步实现与验证。

**目标：** 支持平台管理员取消主办方资格并自动下架其全部活动，同时为登录、找回密码和修改密码提供短信验证码 Mock 能力。

**架构：** 该方案分为两条主链路。第一条是账号安全链路：`send-code` 统一返回开发/演示验证码，登录、找回密码、修改密码都使用同一套验证码校验。第二条是商户治理链路：管理员取消主办方资格后，后端同步更新用户角色、主办方状态、活动状态，并对相关已支付订单发起真实支付宝退款。前端仅负责确认、展示和触发，不承载业务判定。

**技术栈：** Spring Boot + MyBatis-Plus + PostgreSQL + Spring Security PasswordEncoder + Next.js 16 + React 19 + 现有支付宝沙盒退款链路。

---

### 背景与范围

当前系统已经具备以下能力：
- C 端登录、注册、找回密码入口
- `send-code` 接口与短信登录表单
- 用户账号设置页的密码修改能力
- admin/organizer 后台权限体系
- 活动、场次、票档、订单、退款的既有数据模型

本次新增需求有两部分：
1. 平台管理员可以取消主办方资格，取消后其旗下活动必须下架，且相关已支付订单需要直接走真实支付宝退款。
2. 短信验证码能力用于登录、找回密码、修改密码，开发和演示阶段采用固定 Mock 验证码 `666666`。

本次不引入新的审批退款流程，不新增退款申请审核表，也不改造支付核心链路的支付方式。

### 需求拆分

#### A. 主办方资格取消

管理员可以对已存在的主办方执行“取消资格”操作。操作后必须满足：
- 用户角色从 `organizer` 回退为 `user`
- 主办方状态标记为已取消或禁用
- 该主办方旗下所有活动下架
- 该主办方旗下所有场次和票档同步下架
- 与这些活动关联的已支付订单必须发起真实支付宝退款
- 订单页需要展示活动已下架的状态文案

#### B. 单个活动下架

主办方和管理员都可能下架单个活动。下架前必须弹确认提示，明确说明：
- 下架后活动、场次、票档将不可售
- 该活动下的已支付订单将同意并进入退款处理

确认后，后端直接执行真实退款，不创建退款申请，不进入退款审核页。

#### C. 短信验证码 Mock

开发/演示环境中，`send-code` 返回固定验证码 `666666`。该验证码用于：
- 短信登录
- 找回密码
- 修改密码时的短信校验

前端需要保持三个入口都可用，后端统一做验证码校验。

### 设计方案

#### 1. 主办方取消资格

新增一个后端操作入口，由 admin 调用。后端在一次业务操作中完成以下动作：
1. 更新用户表中的 `role` 和主办方状态字段。
2. 查出该主办方旗下所有活动。
3. 将这些活动及其下属场次、票档统一下架。
4. 查出这些活动对应的已支付订单。
5. 对每个订单调用现有支付宝退款链路。
6. 记录每个订单的退款结果，便于前端展示。

这里不新增“待审核退款申请”记录，因为该操作是平台管理员主动执行，视为已同意退款。

#### 2. 单活动下架

在活动管理页中增加下架确认流程。用户触发下架时，前端先展示二次确认弹窗，弹窗文案必须明确退款含义。确认后调用后端活动下架接口，后端执行：
1. 校验操作者是否有权限操作该活动。
2. 下架活动、场次、票档。
3. 查出该活动下的已支付订单。
4. 调用支付宝退款接口。
5. 将订单状态更新为退款中、已退款或退款失败。

#### 3. 短信验证码 Mock

后端 `send-code` 接口在开发/演示阶段直接返回 `666666`，并可在日志中输出，方便演示。

登录页短信登录逻辑改为：
- 手机号
- 验证码
- 验证码必须等于 `666666`

找回密码页改为真正的重置密码页：
- 手机号
- 验证码
- 新密码
- 确认密码

账号设置页修改密码逻辑增加短信验证码字段：
- 原密码
- 短信验证码
- 新密码
- 确认密码

### 数据与状态

#### 用户状态

需要保留或扩展以下状态语义：
- `role = admin | organizer | user`
- 主办方状态字段用于表示当前是否可用

如果现有字段已经能表达取消状态，则复用现有字段；如果不能，则新增一个明确的主办方状态值。

#### 活动状态

活动、场次、票档的下架状态应保持一致，避免出现“活动下架但场次仍可售”的不一致情况。

#### 订单状态

订单退款结果沿用现有订单与退款状态体系。对外展示时补充一个明确的文案：
- 活动已下架
- 退款处理中
- 已退款
- 退款失败

### 前端改动

#### 登录页

- 保留密码登录和短信登录两个入口
- 短信登录默认走 Mock 验证码流程
- 校验失败时给出明确错误提示

#### 找回密码页

- 由“提示页”升级为真正的重置密码页
- 增加短信验证码输入
- 成功后引导回登录页

#### 账号设置页

- 修改密码表单增加短信验证码输入
- 保持原密码校验不变
- 成功后提示用户修改结果

#### 活动管理页

- 下架按钮增加确认弹窗
- 文案必须说明“下架后已支付订单会进入退款处理”

#### 主办方管理入口

- admin 可在后台对主办方执行取消资格操作
- 操作前必须确认后果：该主办方所有活动下架并退款

### 后端改动

#### 用户服务

- `send-code` 返回固定 Mock 验证码
- 登录校验短信验证码
- 找回密码接口使用短信验证码验证并修改密码
- 修改密码接口增加短信验证码校验

#### 商户治理

- 新增取消主办方资格接口
- 新增单活动下架接口的退款联动逻辑
- 对活动、场次、票档的下架操作保持一致性

#### 退款联动

- 复用现有支付宝退款服务
- 不新增退款申请审核步骤
- 对失败退款记录保留错误信息，便于后续补偿处理

### 错误处理

- 验证码错误：返回明确的“验证码错误”提示
- 权限不足：返回 403
- 退款失败：保留订单与退款结果，不影响其它订单处理
- 批量下架中单个订单退款失败：继续处理其余订单，并记录失败项

### 测试策略

#### 后端测试

- 验证短信登录在验证码为 `666666` 时通过
- 验证找回密码在验证码为 `666666` 时可修改密码
- 验证修改密码需要原密码和短信验证码同时正确
- 验证 admin 取消主办方资格后，相关活动被下架
- 验证下架活动后，已支付订单会调用退款链路

#### 前端测试

- 登录页短信登录入口可输入验证码
- 找回密码页可提交手机号、验证码和新密码
- 账号设置页可输入短信验证码修改密码
- 活动下架前有二次确认提示

### 实施顺序建议

1. 先实现短信验证码 Mock 和找回密码/改密流程。
2. 再实现单活动下架确认和退款联动。
3. 最后实现 admin 取消主办方资格和批量下架/退款。

### 风险与约束

- 真实支付宝退款会受沙盒配置、密钥和网络状态影响，需确保退款服务可用。
- 批量退款可能耗时较长，前端应给出明确加载与失败提示。
- 下架与退款需要保持幂等，避免重复执行导致重复退款请求。
- 短信验证码 Mock 仅适用于开发/演示环境，后续接入真实短信时应保持接口形态稳定。
