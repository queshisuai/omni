# Tour/Station 场地申请与 SeatCraft 自由座位块重构设计

## 目标

将现有“活动/场馆/场次/票档”割裂模型重构为符合真实巡演业务的模型：

- `Tour` 表示演出项目或巡演 IP，例如“伍佰 ROCK STAR 2 巡回演唱会”。
- `Station` 表示某个城市站点，例如哈尔滨站、西安站。
- 单场演出也统一表示为只有一个 `Station` 的 `Tour`。
- 任意活动上架前必须先提交场地使用申请，平台审核真实性后才允许上架。
- 相同真实场地可复用历史 SeatCraft 座位图，但不能复用场地使用权。
- SeatCraft 从固定分区模型升级为自由座位块模型，支持方阵、扇形、站区、票档组和响应式预览。

## 核心业务原则

### 没有公共场馆库

平台不提供“公共场馆库”让主办方直接选择后创建活动。

`Venue` 只表示平台识别过的真实物理场地主档，用于：

- 场地去重。
- 相似场地提示。
- 复用历史座位图。
- 保存推荐 SeatCraft 座位图。

任何主办方或 admin 创建活动前，都必须提交自己已经在现实中申请到的场地使用权。平台不负责申请场地，只负责审核用户提交的使用权证明是否真实。

### 使用权来自 VenueApplication

`VenueApplication` 表示一次场地使用申请。

字段包括：

- 申请人 `applicantId`。
- 关联真实场地 `venueId`。
- 场地名称、城市、地址、容量快照。
- 使用有效期 `validFrom / validTo`。
- 使用说明 `proofNote`。
- 附件 URL `proofFileUrl`。
- SeatCraft 座位图快照。
- 默认票档组和默认价格。
- 审核状态、审核人、审核备注。

审核通过后，该申请代表申请人在有效期内拥有该场地的使用权。一个通过的申请可以创建多个活动和站点，但所有场次时间必须落在有效期内。

### 座位图可以复用，使用权不能复用

如果新申请的场地与已有 `Venue` 精确匹配或疑似重复：

- 系统提示候选真实场地。
- 用户仍然必须提交自己的使用申请和证明材料。
- 用户可以复用已有推荐座位图，减少重复绘制。
- 用户也可以重新绘制本次申请的座位图。
- admin 审核通过时可选择是否将本次座位图设为 `Venue` 推荐座位图。

活动创建时永远复制 `VenueApplication` 的座位图快照，不直接依赖 `Venue` 主档。

## Tour / Station 模型

### Tour

`Tour` 是演出项目主实体。

它保存巡演或单场项目的公共信息：

- 标题。
- 艺人。
- 分类。
- 主海报。
- 简介。
- 宣传文案。
- 基础审核状态。
- 创建人和归属主办方。

巡演型项目有多个 `Station`。单场活动也表示为只有一个 `Station` 的 `Tour`。

### Station

`Station` 是城市站点子实体。

它保存站点差异信息：

- 城市。
- 站点名称，例如“哈尔滨站”。
- 站点专属海报或文案。
- 绑定的 `VenueApplication`。
- 活动座位图副本。
- 活动票档组价格。
- 上架状态。

`Station` 继承 `Tour` 的基础信息，但允许覆盖部分展示内容。暂定采用分层继承：Tour 提供默认信息，Station 可覆盖局部信息。

### 审核关系

采用两级审核：

- `Tour` 层审核演出项目基础信息。
- `Station` 层审核场地使用申请、座位图和时间安排。

某个站点审核通过后可单独上架，其他站点可以继续待审核。

## 活动草稿与发布状态

现有 `activity.status` 不再承担创建流程语义，只表示启用/停用。

新增 `publishStatus`：

- `draft`：草稿。
- `pending_venue`：等待场地申请审核。
- `pending_layout`：等待座位图确认。
- `pending_sessions`：等待场次配置。
- `ready`：可发布。
- `published`：已发布。
- `offline`：已下架。

创建演出第一步填写基础信息后立即落库为草稿。场地申请未通过前，活动或站点只能保存草稿，不能对 C 端展示。

场地申请审核通过后，系统自动推进状态，并通知主办方继续配置座位图、票价和场次。

## 主办方工作台

主办方端不再以“场馆管理 / 活动管理 / 场次管理 / 票档管理”割裂操作。

改为围绕演出项目组织：

- `我的演出`。
- `创建演出`。
- `场地申请记录`。
- `订单`。

`创建演出` 使用分步向导：

1. 创建 Tour 或选择已有 Tour，保存草稿。
2. 创建或选择 Station。
3. 提交场地使用申请，填写有效期、说明、附件 URL。
4. 系统提示相同或疑似场地，可复用座位图。
5. SeatCraft 配置座位图和默认票档组价格。
6. 场地审核通过后配置活动票价覆盖。
7. 添加场次排期。
8. 发布确认。

admin 也使用同一套显示逻辑，只是拥有审核入口和全局管理能力。admin 当前模拟活动后续也应迁移到该模型。

## SeatCraft 自由座位块模型

### Block 取代 Section

开发阶段不做旧 `section` 兼容，直接重建 SeatCraft 数据模型。

核心概念：

- `SeatBlock`：座位块。
- `SeatOverride`：单座位例外。
- `TicketGroup`：票档组。

块类型：

- `gridBlock`：方阵座位块。
- `arcBlock`：扇形/弧形座位块。
- `standingBlock`：站区块。

### gridBlock

用于规则方阵座位。

参数：

- `x / y`。
- `rotation`。
- `rows / cols`。
- `rowSpacing`。
- `seatSpacing`。
- `scale`。

### arcBlock

用于高度自由的扇形座位。

参数：

- `centerX / centerY`。
- `rotation`。
- `rows`。
- `seatsPerRow`。
- `innerRadius`。
- `rowSpacing`。
- `arcStartAngle`。
- `arcEndAngle`。
- `seatSpacing` 或自动均分。
- `scale`。

一个半圆可以拆成左右两个 `arcBlock`：

- 左侧看台使用一段角度。
- 右侧看台使用另一段角度。
- 中间可以放置 `gridBlock` 方阵。

每个块可自由移动、旋转、复制、镜像。默认开启对齐吸附，高级模式可关闭吸附。

### standingBlock

用于站区。

参数：

- `x / y`。
- `width / height`。
- `capacity`。
- `rotation`。
- `ticketGroupKey`。

站区没有具体座位号。场次创建时不展开具体座位，只生成票档库存。

站区可以和座位区混合到同一票档组，但 UI 必须给出风险提示。

### SeatOverride

大部分座位由 block 参数动态计算。只存例外座位：

- `blockId`。
- `rowNo`。
- `seatNo`。
- `status`：`visible / hidden / deleted`。
- `dx / dy`：单座位微调偏移。
- `customLabel`：手动座位名。

不支持单座位单独定价，也不支持单座位单独改票档。

### 座位编号

默认自动编号。特殊座位可手动重命名，例如 `A01`、`A02`。

## TicketGroup 自动票档

场次管理不再新增票档。

票档由 SeatCraft 的 `TicketGroup` 自动生成。

规则：

- 新建座位块默认生成一个票档组。
- 多个 block 可绑定同一个 `ticketGroupKey`。
- 同一票档组可以跨不同 block 类型。
- 同一票档组保留来源块列表 `sourceBlockIds`。
- 场馆申请阶段配置默认价格。
- 活动或站点阶段可覆盖价格。
- 同一活动或站点内，同一个票档组价格必须一致。

场次创建时：

- 按 `ticketGroupKey` 聚合 block。
- 创建实际 `ticket_type`。
- `ticket_type.total_stock` 等于所有来源块可售座位数加站区容量。
- `ticket_type.remain_stock` 同上。
- 生成 `session_seat` 时记录来源 block、票档组、ticketTypeId。

## 库存与下单

预览和编辑时座位可动态计算。

发布或场次创建时，根据 block 参数和 override 展开为 `session_seat` 快照。

选座下单：

- 前端传座位 ID。
- 后端校验座位属于同一场次、同一票档。
- 后端锁定座位并扣减对应票档库存。

非选座下单：

- 前端传 `ticketTypeId + quantity`。
- 后端按 `ticket_type.remain_stock` 扣减。
- 站区按数量扣减，不涉及具体座位。

所有金额和库存以后端为准，前端只展示。

## SeatCraft 预览适配

座位图预览支持两档模式：

- `完整视图`：整张座位图缩放进容器，不裁切。
- `放大查看`：座位保持可读大小，支持拖拽或滚动。

桌面端默认完整视图，提供放大按钮。移动端默认完整视图，点击进入放大模式。

缩放规则：

- 使用原始 `canvasWidth / canvasHeight` 计算比例。
- 缩放只影响视觉，不修改坐标数据。
- grid、arc、standing 都使用同一层 transform，避免坐标错位。

## 场地冲突

申请阶段不因有效期重叠直接阻止审核。

真正创建场次时检查同一真实场地同一时间段是否已有场次。如果冲突，拒绝创建场次。

## 测试数据清理

本次验证产生的数据需要清理：

- `测试场馆 id=16`。
- 对应 `venue_default_layout`。
- 对应 `venue_default_layout_section`。

后续所有 API 验证必须遵循：

- 测试数据使用统一前缀，例如 `__TEST__`。
- 流程包含 `创建 -> 验证 -> 清理`。
- 清理按外键依赖从子表到父表删除。
- 验证失败也尽量执行 cleanup。

## 非目标

- 不实现平台代主办方申请现实场地。
- 不允许绕过 VenueApplication 直接使用 Venue 创建活动。
- 不做旧 section 数据兼容迁移。
- 不支持单座位单独定价。
- 不支持单座位独立票档。

## 风险

- Tour/Station 会影响现有 Activity/Session 命名，需要谨慎拆迁。
- SeatCraft 自由 block 模型改动较大，应分阶段落地。
- session_seat 展开会带来数据量增长，需要注意批量插入性能。
- 票档组跨 block 混合站区和座位区时，UI 必须明确提示，否则用户会误解选座规则。

## 订单可见性与用户侧删除

订单数据不允许物理删除。用户前端的“删除订单”仅表示用户侧隐藏，不影响后台、商户、支付、退款、验票、售后和统计。

### admin 查看订单

admin 可以按用户信息查看订单：

- 用户 ID。
- 手机号。
- 用户名或昵称（如果用户资料支持）。
- 订单号。
- 活动 / Tour / Station。
- 订单状态。

admin 查询结果不受用户侧隐藏影响，始终能看到完整订单记录。

### 商户查看订单

organizer 只能查看自己名下 Tour / Station / 活动产生的订单。

规则：

- 订单关联的活动归属该 organizer 时可见。
- 订单归属其他 organizer 时不可见。
- 用户是否隐藏订单不影响 organizer 查看。

### 用户侧删除与回收站

用户删除订单时，只将订单移入用户侧回收站。

建议新增订单可见性字段或独立可见性表，至少记录：

- `user_id`。
- `order_id`。
- `visibility_status`：`visible / trashed`。
- `trashed_at`。
- `expire_at`。
- `restored_at`。

回收站保留 7 天。7 天后，订单仍不从数据库删除，只是不再展示在用户端回收站，也不可由用户恢复。

### 删除限制

以下订单允许用户侧隐藏：

- 待支付。
- 已取消。
- 已退款。
- 已支付且未退款，但活动或场次已结束。

以下订单不允许用户侧隐藏：

- 已支付且未退款，并且活动或场次仍在有效期内。
- 退款中。
- 售后中。

判断“活动仍在有效期内”时优先使用场次结束时间。如果没有结束时间，则使用开始时间加默认演出时长或业务配置。

### 恢复订单

用户可在回收站 7 天内恢复订单显示。

恢复后：

- 用户订单列表重新显示该订单。
- admin 和 organizer 可见性不变。
- 订单支付、退款、验票状态不变。
