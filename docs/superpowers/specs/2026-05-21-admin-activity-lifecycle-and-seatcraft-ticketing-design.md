# 后台活动生命周期与 SeatCraft 票档设计

## 背景

当前后台活动管理存在两类问题：

- 活动删除直接硬删 `activity`，当活动已有场次、票档、座位或订单关联时会触发数据库外键约束，导致接口 500。
- 场次管理中的新增票档仍偏表单式，不符合 SeatCraft 座位图内选择区域/座位并创建票档的目标体验。

本设计统一 admin、商户和 C 端围绕活动发布、下架、退款、删除、票档创建的业务规则。

## 目标

- admin 可审核商户申请、活动发布申请，并可下架活动。
- 商户可管理自己旗下活动的增删改查。
- 商户已有活动可以下架；删除活动必须填写原因。
- 已发布且存在购票订单的活动，必须先完成退款闭环，用户订单显示已退款后才允许最终删除。
- 场次管理新增票档必须进入 SeatCraft 座位图，在座位图上选择区域/座位并创建票档。
- 历史模拟数据和旧点阵座位图需要迁移为 SeatCraft layout；迁移完成后移除旧点阵图主流程。
- 避免跨服务 Mapper、Entity、SQL join，继续通过 internal API 完成订单和退款协作。

## 非目标

- 不引入 MQ、outbox、CDC 或双写。
- 不恢复评价/动态系统。
- 不把 `sql/local/*` 纳入生产迁移链路。
- 不让 ticket 服务直接访问 order/payment/user 表。

## 角色规则

### 普通用户

- 可以提交商户认证申请。
- admin 审核通过后，用户角色变为 `organizer`，才能进入商户后台。

### 商户

- 只能管理自己旗下活动。
- 可以创建活动草稿、编辑活动草稿、提交发布申请。
- 对已发布活动可以主动下架，C 端立即不可购买。
- 删除活动必须填写原因。
- 已发布且有已支付订单的活动，必须先进入退款流程；存在退款失败、结果未知或需人工处理时，不能最终删除。

### admin

- 可以审核商户认证申请。
- 可以审核活动发布申请。
- 可以下架任意活动。
- 可以查看活动下架、退款、删除原因和异常退款处理记录。

## 活动生命周期

活动使用明确状态流转表达业务阶段。实现时可复用现有 `status` + `publish_status`，也可增加更清晰的审计表；实际实施计划中再确定最小迁移方式。

| 状态 | 含义 | C 端可见/可买 | 商户动作 | admin 动作 |
|:---|:---|:---|:---|:---|
| `draft` | 草稿 | 不可见 | 编辑、删除、提交审核 | 可查看 |
| `pending_publish` | 待发布审核 | 不可见 | 撤回、查看 | 通过、拒绝 |
| `published` | 已发布 | 可见可买 | 编辑受限、下架 | 下架 |
| `deactivating` | 下架退款处理中 | 可见但不可买或不展示购票入口 | 查看退款进度 | 查看/处理异常 |
| `deactivated` | 已下架 | 不可买 | 删除、重新提交审核 | 上架/处理 |
| `deleted` | 已删除 | 不可见 | 不展示 | 审计可查 |

## 下架与退款规则

### 无已支付订单

- 商户或 admin 下架活动后，活动、场次、票档统一置为不可售。
- 活动进入 `deactivated`。
- 商户删除时必须填写原因，可直接标记为 `deleted`。

### 有已支付订单

- 商户或 admin 点击下架时必须确认退款。
- ticket 服务通过 order internal API 查询相关场次的已支付订单。
- payment 服务通过 internal API 执行直接退款。
- 退款成功的订单由 order 服务更新为 `STATUS_REFUNDED = 4`，C 端订单页展示“已退款”。
- 退款失败、结果未知、补偿所需的订单进入异常处理列表。
- 只要存在异常退款记录，活动不能最终删除，只能保持 `deactivating` 或 `deactivated` 并展示异常提示。
- 全部订单退款闭环后，商户可填写原因并删除活动，活动标记 `deleted`。

## 删除规则

### 草稿/未发布活动

- 商户填写原因后可直接删除。
- 若没有外键关联，可硬删。
- 若已有 SeatCraft 草稿布局、场次草稿等关联数据，优先标记 `deleted`，避免外键导致 500。

### 已发布活动

- 不允许直接硬删。
- 必须先下架。
- 如有已支付订单，必须完成退款闭环。
- 删除动作只做逻辑删除，保留活动、场次、票档、座位、订单快照和退款审计。

## SeatCraft 票档创建

SeatCraft 是 B 端票档配置和 C 端用户选座的唯一目标交互。旧点阵座位图只用于迁移前识别历史数据，不再作为新功能目标形态。

### 数据迁移策略

- 对现有模拟数据和历史 `session_seat` 点阵数据生成兼容的 SeatCraft layout。
- 迁移逻辑按场次聚合座位，推断行、列、区域和基础坐标，生成 SeatCraft 可渲染的 sections / seats / blocks。
- 若历史数据已有票档 ID，则迁移时把票档绑定到对应 SeatCraft 区域或座位。
- 无法可靠推断区域的历史数据，生成一个默认区域，确保仍能在 SeatCraft 中展示和继续编辑。
- 迁移完成后，B 端和 C 端座位页面都读取 SeatCraft layout；旧点阵组件从主流程移除。
- 若某场次仍缺 SeatCraft layout，页面提示“请先配置座位图”，不再退回点阵图。

### 入口

- 场次管理不再提供简单表单式新增票档作为主入口。
- 点击“新增票档”进入该场次的 SeatCraft 座位图。
- SeatCraft 画布展示该场次的分区、座位和已有票档绑定状态。

### 创建流程

1. 商户/admin 进入场次 SeatCraft 票档编辑器。
2. 选择一个或多个未绑定票档的区域/座位。
3. 填写票档名称、价格、说明等必要信息。
4. 系统根据选择的可售座位自动计算库存。
5. 保存后创建 `ticket_type`，并把选中区域/座位绑定到该票档。
6. C 端活动详情按票档切换时，座位图自动聚焦到该票档对应区域。

### 约束

- 不允许同一座位同时绑定多个票档。
- 不允许对已售出、锁定或不可售座位重新绑定票档。
- 修改票档绑定时必须校验订单影响；已产生订单的座位不允许被移出原票档。
- C 端下单必须提交后端真实可售座位 ID，不能提交前端临时生成的伪座位。

## 前端交互

### 商户活动列表

- 草稿活动显示“编辑、提交审核、删除”。
- 待审核活动显示“查看、撤回”。
- 已发布活动显示“下架”。
- 已下架活动显示“删除”，点击时要求填写删除原因。
- 退款异常活动显示异常数量和处理入口。

### admin 活动列表

- 支持审核发布申请。
- 支持下架活动，并提示是否触发退款。
- 支持查看删除原因、退款异常和处理记录。

### C 端订单页

- 订单状态 `4` 继续展示为“已退款”。
- 已下架/删除活动不影响用户查看历史订单。

### C 端选座页

- 活动详情使用 SeatCraft 选座组件作为唯一主入口。
- 选择票档后，SeatCraft 画布自动拉近并聚焦到该票档绑定区域。
- 用户只能在该票档对应的真实可售座位中选择。
- 历史点阵组件迁移完成后从 C 端主流程移除。

## 后端边界

- `java-ticket` 只拥有活动、场次、票档、座位、SeatCraft 布局状态。
- `java-order` 拥有订单状态和订单快照。
- `java-payment` 拥有支付和退款流水。
- ticket 查询已支付订单必须走 order internal API。
- ticket 发起退款必须走 payment internal API。
- payment 更新订单退款状态必须走 order internal API。
- 所有 internal API 必须校验 `X-Internal-Token`。

## 错误处理

- 外键约束不应再暴露为全局 500。
- 对有关联数据的活动删除，统一走逻辑删除或业务拒绝。
- 删除原因为空返回 400。
- 未完成退款闭环时删除已发布活动返回 400，并提示仍有退款未完成或需人工处理。
- 商户操作非本人活动返回 403。

## 测试策略

- 单测覆盖商户删除草稿活动。
- 单测覆盖有关联活动删除时逻辑删除，不硬删。
- 单测覆盖已发布且有已支付订单时必须先退款。
- 单测覆盖退款异常时活动不能最终删除。
- 单测覆盖 admin 下架活动。
- 测试覆盖历史点阵数据生成 SeatCraft layout。
- 前端类型检查覆盖活动列表动作和 SeatCraft 票档入口。
- 边界检查继续运行 `scripts/verify-microservice-boundaries.ps1`，确保不新增跨服务 Mapper 或 SQL。

## 验收标准

- 商户可以管理自己旗下活动，不能管理他人活动。
- admin 可以下架活动。
- 商户删除活动必须填写原因。
- 删除有关联数据的活动不再 500。
- 有已支付订单的活动下架会触发自动退款；退款成功后用户订单显示已退款。
- 存在退款异常时活动不能最终删除。
- 场次新增票档进入 SeatCraft 座位图完成创建和绑定。
- C 端选票档后座位图自动聚焦对应区域。
- 旧模拟/历史点阵座位数据迁移后可在 SeatCraft 中展示。
- 迁移完成后，B 端和 C 端座位主流程不再展示旧点阵图。
