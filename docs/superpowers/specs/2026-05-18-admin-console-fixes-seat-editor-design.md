# 后台管理修复与场馆座位编辑器设计

## 背景

当前后台仍有几处闭环缺失：

- 管理员取消用户主办方资格后，用户重新进入商户入驻页时仍容易看到“已通过”，状态说明里也没有“主办方资格已取消”。
- 平台管理后台首页只有活动数，总票档数和总订单数仍显示占位符。
- 活动管理列表的“编辑”按钮已存在，但目标编辑页未实现。
- 场馆管理列表的“配置区域”入口只提供基础区域生成面板，尚未形成完整的可视化座位模板编辑体验。

本设计目标是在不重做整个后台架构的前提下，补齐这些后台管理闭环，并对座位模板编辑加入交易安全边界。

## 目标

- 商户入驻页能准确区分“申请曾通过”和“当前主办方资格已取消”。
- 后台首页统计真实展示活动数、票档数、已支付订单数。
- admin 统计全平台数据，organizer 只统计当前账号可管理的数据。
- 活动编辑页面只负责活动基础信息，场次和票档继续在场次管理中维护。
- 场馆座位模板支持可视化座位级编辑：新增、删除、启用/禁用、改号、移动。
- 场馆模板修改后自动安全同步到无交易数据的场次；已有锁座、售座或订单关联的场次跳过。

## 非目标

- 不重构整个后台导航和页面架构。
- 不把活动、场次、票档合并成一个大型编辑页。
- 不对已有交易场次做强制覆盖同步。
- 不实现复杂图形设计器能力，例如框选、旋转、多层楼座、SVG 自由绘制。

## 角色与统计口径

后台首页新增三项统计：

- `activityCount`：活动数。
- `ticketTypeCount`：票档数。
- `paidOrderCount`：已支付订单数。

统计规则：

- admin：统计全平台活动、票档、已支付订单。
- organizer：只统计当前账号名下活动、这些活动下票档、这些活动下已支付订单。
- 订单统计只包含状态为已支付的订单，即后端订单状态 `2`。
- 前端卡片文案使用“已支付订单数”，避免与全部订单混淆。

## 商户资格取消状态

商户入驻页需要把两种状态拆开表达：

- 申请状态：来自入驻申请记录，仍可显示 `0 待审核`、`1 已通过`、`2 已驳回`。
- 当前资格状态：来自用户的 `organizerStatus` 和 `role`，当 `organizerStatus = 3` 且 `role = user` 时，当前资格为“已取消资格”。

页面行为：

- 已取消资格用户不显示“进入商户后台”。
- 已取消资格用户可以重新提交入驻申请。
- 当前状态提示优先展示“主办方资格已取消，可重新提交入驻申请”。
- 状态说明增加 `3 已取消资格`，说明为“账号已降级为普通用户，可重新提交入驻申请”。
- 保留历史申请信息，但避免用“已通过，可进入后台”误导用户。

## 后台统计接口设计

推荐新增后端统计接口，由后端负责权限过滤，前端只展示结果。

### 票务服务统计

在 `java-ticket` 后台接口中新增统计能力，用于计算当前用户可管理范围内的活动数和票档数。

返回结构建议：

```json
{
  "activityCount": 30,
  "ticketTypeCount": 90,
  "paidOrderCount": 12
}
```

活动和票档统计由 `java-ticket` 根据用户角色计算：

- admin 不加 `organizer_id` 过滤。
- organizer 加 `activity.organizer_id = userId` 过滤。

### 订单统计

`paidOrderCount` 需要从 `java-order` 获取。实现可选路径：

- 在 `java-order` 新增后台统计接口，接收可管理的 sessionId 列表并返回状态为 `2` 的订单数量。
- 或在 `java-ticket` 内部通过 `INTERNAL_API_TOKEN` 调用订单服务内部接口聚合统计。

推荐由 `java-ticket` 暴露统一的 `/api/ticket/admin/summary` 给前端，内部再调用 `java-order` 的内部统计接口。这样前端不需要同时理解票务服务和订单服务的权限边界。

## 活动基础编辑

新增活动编辑页：

- 路径：`/console/activities/[id]/edit`
- 功能：编辑活动基础信息。
- 字段：活动名称、分类、艺人、海报、描述。
- 保存接口：复用 `PUT /api/ticket/admin/activities/{id}`。
- 权限：沿用后端现有规则，admin 可编辑全部活动，organizer 只能编辑自己名下活动。

页面不管理场次和票档，只提供明确入口：

- “管理场次/票档”跳转到 `/console/sessions?activityId=<id>`。
- 场次管理页读取 `activityId` 查询参数并作为默认筛选条件。

活动上下架仍留在活动列表，避免编辑表单和退款风险操作混在一起。

## 场馆座位模板编辑器

场馆管理的“配置区域”升级为独立座位模板编辑体验。

建议路径：

- `/console/venue/[id]/seats`

核心能力：

- 区域管理：新增区域、编辑区域名称、颜色、排序、删除区域。
- 批量生成：按排数、每排座位数、起始排号、起始座号生成座位。
- 座位编辑：新增单个座位、删除座位、启用/禁用座位、修改排号、座号、显示名称。
- 座位移动：保存座位展示坐标 `x/y`，排号和座号作为业务编号，不等同于展示坐标。
- 可视化展示：按区域颜色展示座位点阵，点击座位后在侧边编辑属性。

数据字段建议：

- `venue_area` 保留区域名称、颜色、排序等字段。
- `venue_seat` 增加或确认具备以下字段：
  - `row_no`：业务排号。
  - `seat_no`：业务座号。
  - `seat_label`：展示名称，可为空，为空时由排号和座号生成。
  - `x`：展示横坐标。
  - `y`：展示纵坐标。
  - `status`：座位状态，至少支持正常和禁用。

如果现有表缺少 `seat_label`、`x`、`y` 或 `status`，需要补充迁移 SQL，并同步实体和 DTO。

## 模板同步规则

场馆模板变更后自动触发安全同步，只同步无交易数据的场次。

可同步条件：

- 场次使用当前场馆。
- 场次下不存在锁定座位。
- 场次下不存在已售座位。
- 场次下不存在订单座位关联。

跳过条件：

- 存在 `LOCKED` 座位。
- 存在 `SOLD` 座位。
- 存在 `order_seat` 关联记录。

同步行为：

- 对可同步场次，按最新场馆模板重建或增量更新 `session_seat`。
- 对跳过场次，不修改其 `session_seat`，避免破坏订单座位关系。
- 接口返回同步结果：同步场次数、跳过场次数、跳过场次列表或摘要。

前端提示：

- “已同步 X 个未交易场次，跳过 Y 个已有交易场次。”
- 如果有跳过项，提示“已有交易数据的场次不会自动覆盖，请按实际业务人工处理”。

## 错误处理

- 统计接口失败时，后台首页显示加载失败提示，不使用占位符伪装真实数据。
- 活动编辑保存失败时展示后端错误信息。
- 座位模板保存失败时保留当前编辑状态，提示失败原因。
- 删除区域或座位时，如果已经被不可同步场次或票档绑定使用，后端返回明确错误，前端展示原因。
- 自动同步跳过不视为接口失败，只作为成功响应中的部分结果展示。

## 测试计划

后端测试：

- 商户资格取消后，用户信息返回 `role=user`、`organizerStatus=3`。
- admin 统计全平台活动、票档、已支付订单。
- organizer 统计仅包含自己名下活动、票档、已支付订单。
- 未支付、已取消、已退款订单不计入 `paidOrderCount`。
- 活动编辑权限：admin 可编辑任意活动，organizer 只能编辑自己活动。
- 座位模板编辑：新增、修改、删除、禁用、移动座位。
- 模板同步：无交易场次会同步，有锁座、售座或订单关联的场次会跳过。

前端验证：

- 取消资格用户进入商户入驻页显示“主办方资格已取消”，不显示后台入口，可重新提交。
- 后台首页三张统计卡片展示真实数字。
- 活动列表编辑按钮进入编辑页，保存后活动列表字段更新。
- 编辑页“管理场次/票档”能带 `activityId` 跳转并筛选。
- 场馆“配置区域”进入座位模板编辑器，可完成座位级编辑并看到同步结果提示。

## 实施顺序建议

1. 修复商户资格取消状态展示。
2. 增加后台统计接口与首页真实统计。
3. 实现活动基础编辑页和场次管理筛选入口。
4. 增加座位模板数据字段和后端编辑接口。
5. 实现场馆座位模板编辑器页面。
6. 实现模板安全自动同步和提示。
7. 运行后端测试、前端类型检查，并做后台关键流程手工验证。

## 风险与约束

- 座位模板同步涉及 `venue_seat` 和 `session_seat`，必须严格跳过已有交易数据的场次。
- 座位移动需要保存展示坐标，不能覆盖业务排号和座号。
- 删除区域和座位必须考虑票档区域绑定、场次快照、订单座位关系。
- 统计接口跨票务和订单服务，内部 token 配置必须一致。
- 后端代码修改后需要重新编译并重启对应服务才能生效。
