# Team Grab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build first-version team grab where 2-6 confirmed members share one team request, one batch seat lock, one leader-paid order, and member seat assignments after payment.

**Architecture:** Team state lives in grab-service because it is transaction orchestration, not ticket inventory or order persistence. Ticket-service owns strategy-based group seat locking with row-level locks. Order-service owns the leader-paid team order and order-seat rows, while grab-service links that paid order back to team members through `team_seat_assignment`.

**Tech Stack:** NestJS 10, Jest, Redis/ioredis, PostgreSQL, Spring Boot 2.7, MyBatis-Plus, Seata, JUnit/Mockito, Next.js 16, React 19, TypeScript.

## Decisions

- First version supports only same-session, same-ticket-type team grab.
- Team size is 2-6 confirmed members.
- Only leader can change session, ticket type, strategy, and fallbacks.
- Any confirmed member can trigger grab, but Redis and DB idempotency allow only one active team grab request.
- Payment is leader unified payment. `order.user_id` is the leader.
- First version purchase-limit accounting is by leader quantity.
- Team locking supports seat-based sessions. Seatless standing team grab returns a clear unsupported error in this version.
- Seat assignment is leader first, then confirmed members by `join_time`.
- Notifications are in-app messages through `java-notification` internal API.
- Payment timeout rule: order cancellation/timeout changes team `LOCKED -> EXPIRED`, releases seats through existing order expiration, and allows leader or confirmed members to trigger again.
- Cross-service boundary rule: order-service must use order-owned seat label data and must not query ticket-service tables directly.

### Team Status Mapping

| Status | Meaning | Retry Rule |
| --- | --- | --- |
| `READY` | Confirmed member count is 2-6 and the team can trigger a grab. | Can trigger. |
| `GRABBING` | A team grab request is queued or processing. | Cannot trigger another request. |
| `LOCKED` | Order was created and the leader payment window is open. | Cannot trigger until order cancels or expires. |
| `PAID` | Payment succeeded and all member assignments were written. | Terminal success. |
| `FAILED` | Current grab attempt failed before order creation. | Can trigger again. |
| `EXPIRED` | Locked order was cancelled or timed out; members stay in the team. | Can trigger a new `team_grab_request`. |

- [ ] **Step 5: Implement strategy selection**

In `TicketSalesInternalService.lockTeamSeats()`:

1. Annotate the method with `@Transactional(rollbackFor = Exception.class)`.
2. Validate `quantity` is 2-6.
3. Validate session, activity, and ticket type are sellable using the same sellable predicate as quote and normal lock flows.
4. Select available seats `FOR UPDATE SKIP LOCKED`.
5. Keep the candidate select and the update that writes `lock_request_id` inside the same transaction.
6. Try strategies in this order: primary, then fallbacks.
7. `STRICT_CONTIGUOUS`: same `layoutSectionId` or `seatBlockId`, same `rowNo`, consecutive `seatNo`.
8. `SAME_BLOCK`: same `layoutSectionId` or `seatBlockId`, any seats.
9. `SAME_TICKET_TYPE`: first available seats sorted by block/row/seat.

## Acceptance Mapping

- 4 members click concurrently, one request: Task 6 and Task 10.
- Contiguous seats lock when enough seats exist: Task 4.
- Fallback locks same-ticket seats when contiguous is unavailable: Task 4 and Task 10.
- Leader unpaid timeout releases seats: Task 5 reuses order expiration and Task 7 marks team expired.
- Order timeout changes team `LOCKED -> EXPIRED` and permits a new trigger with the same members: Task 7.
- Ticket locked but order not created is recovered and released: Task 7.
- Paid order creates member assignments: Task 7.
- Locked team prevents leave and duplicate session team: Task 2.
- No oversell: Task 4 uses `FOR UPDATE SKIP LOCKED`; order-service never confirms seats without ticket-service validation.
- Final confirmation remains in ticket/order services: Task 5 and existing payment confirmation flow.
- Team order details and assignments use order-owned `order_seat.seat_label`, not cross-service ticket DB reads: Task 5.
- Production-split database rebuilds include all new SQL through `sql/production-split/manifest.json`: Tasks 1, 4, and 5.

## Known Risks

- `session_seat.lock_request_id` is a new ownership field and must be cleared by all release paths.
- `markSeatSold()` must also clear `lock_request_id`; otherwise sold seats retain a stale lock owner.
- A process crash after ticket lock and before order creation leaves pre-order locks; `team-lock-recovery.service.ts` must release them by `requestId`.
- Order-service team order must never re-lock prelocked seats, otherwise team flow will fail after ticket-service lock.
- Order-service must never query ticket DB for seat labels; labels are copied into `order_seat.seat_label` from the team lock response.
- If payment sync is scheduler-only, paid assignments may lag. The explicit `sync-paid` endpoint reduces visible delay.
- Split payment and member-level purchase limits are intentionally excluded from this version.

## Self-Review

- Scope is focused on first-version leader-paid team grab.
- No cross-session, cross-ticket, waitlist, split payment, or replacement-member work is included.
- Boundaries are preserved: ticket-service owns inventory locks, order-service owns order and order seats, grab-service owns team orchestration and assignments.
- Every acceptance criterion maps to at least one task.
